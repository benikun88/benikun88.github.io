FULL-STACK TESTING↗ 01

End-to-end automation

Python, Playwright, and Pytest frameworks for frontend and backend coverage on a multi-region SaaS platform.

  • Python
  • Playwright
  • Pytest
  • E2E

Tests read like the manual steps, so a reviewer can follow them without reading the automation API.

  • A base page class and one wrapper per page, dialog, or wizard. Playwright types stay out of the tests.
  • Logs nested per phase and per step. Each test keeps its own logs, screenshots, and network log.
  • Steps wait for the screen to show the state they need instead of sleeping, and locators work on the old and the new UI.

TEST DATA↗ 02

Parallel-safe runs

Workers that run together share one login, and scarce test data is handed out once, under a lock.

  • pytest-xdist
  • File locks
  • TOTP MFA
  • Faker

Parallel runs should not fight over the same account or the same phone number.

  • pytest-xdist workers share one logged-in session, created under a file lock. Login uses TOTP-based MFA.
  • A pool of SMS-capable phone numbers is taken and released under file locks with timeouts.
  • API clients create unique test data and check the responses. Fixtures tear it down so the next run starts clean.

REPORTING↗ 03

Reports that separate flakes

JUnit XML becomes a per-run HTML report and a cumulative dashboard that tells a flake from a real failure.

  • JUnit XML
  • Allure
  • S3
  • CloudFront
  • Slack

A job log does not show whether the suite is improving, or whether a failure is flaky.

  • Per-run HTML reports, plus a dashboard with a pass-rate trend, a daily chart, and a run-history matrix.
  • Flaky versus broken comes from run history, not from a guess.
  • Published to S3 behind CloudFront. Slack notifications carry a direct link to the run.

06 / Open source

A public
sample suite.

A small public stand-in for the same approach. It targets practicesoftwaretesting.com only, and the catalog there is synthetic.

Eight UI checks cover search, a category filter, price sort, a product page, cart math, sign-in, invoices (the shop's order history), and an out-of-stock control. Three API checks validate product and category payloads with pydantic.

Page objects use role-based locators, and there are no fixed sleeps. Sign-in uses the shop's built-in customer account. Reports land in reports/junit.xml and reports/report.html.

The shop refuses headless Chromium, so the suite runs a headed browser. On Linux, wrap it in xvfb-run.

Sample suite on GitHub ↗ 
cd sample-suite
python3.13 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python -m playwright install chromium
xvfb-run -a python -m pytest
